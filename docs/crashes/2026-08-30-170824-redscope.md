## Assessment: finding #10 ruled out, two remaining candidates found and fixed

`crash-audit-2026-08-29.md` finding #2 and its fix (`d8ac682`) addressed an
unguarded `spawnedObject as ScriptedPuppet` cast in the first loop of
`SpawnRequestFinished` (`DynamicSpawnSystem.reds`, then lines ~29-42). That
fix is confirmed still in place and correct, and was live for many hours
before this crash — ruling out "stale pre-fix build" as the explanation
for this recurrence (the open question `crash-audit-2026-08-30.md` left
open).

**Confirmed directly by the user**: this crash was produced by the project
in the exact working-tree state investigation began from — i.e. the build
that crashed already included finding #10's fix (the
`GetPuppetStateBlackboard()` guard on `NPCPuppet.ChangeHighLevelState(...)`),
even though it was uncommitted. That guard being present and the crash
still happening **rules out finding #10** as this crash's cause.

What was *not* yet in that build, and is a genuine null-deref risk in the
same function, found this session: further down `SpawnRequestFinished`, in
the vehicle command loop, three chained accessor calls had no
`IsDefined()` guard on the accessor's result before calling a method on
it — `wheeledObject.GetAIComponent().SetInitCmd(...)` (two call sites) and
`wheeledObject.GetVehicleComponent().ToggleSiren(true, true)`.
`GetAIComponent()`/`GetVehicleComponent()` can return `null` — confirmed by
CDPR's own code, which null-checks `GetVehicleComponent()`'s result
elsewhere (`vehicleComponent.reds:5125`) before using it, even though
vanilla's own `DynamicSpawnSystem.SpawnCallback` chains
`GetAIComponent().SetInitCmd(...)` unguarded (the same trap this mod
copied when the vehicle-chase code was originally written). A vehicle
present in `requestResult.spawnedObjects` isn't guaranteed to have these
components fully attached by the time `SpawnRequestFinished` runs.

Also not yet fixed in that build, and closed the same pass: the first
loop's per-entry `spawnedObject` wasn't `IsDefined()`-checked before
calling `.IsPuppet()`/`.IsVehicle()` on it, unlike the sibling
`SpawnCallback` method which does guard its own `spawnedObject` parameter
at entry.

These two remaining candidates — the `GetAIComponent()`/
`GetVehicleComponent()` chains and the unguarded `spawnedObject` — were
both still present in the crashing build, and both plausibly resolve to
the same native offset (`+0x2F098B`), since that address looks like a
shared "read a field through a null object pointer" fault site rather than
something specific to one call site. The fingerprint can't be used to pick
between them, but with finding #10 eliminated, one of these two is now the
leading explanation rather than one candidate among three.

**Fix applied this session**: guard the three chained accessors
(`GetAIComponent()`, `GetVehicleComponent()`) with `IsDefined()` before
calling through them, and guard `spawnedObject` itself at the top of the
first loop. See `DynamicSpawnSystem.reds`.

If this fingerprint recurs on a build carrying all of this session's
fixes plus finding #10's, that would rule out this function's currently-
known gaps entirely and point at something else again.
