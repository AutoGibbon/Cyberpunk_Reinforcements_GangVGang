Confirmed from the cache: `r6/cache/modded/final.redscripts.modded`'s mtime
was untouched from before this launch and didn't update until the

unrelated logic bug — see below — had been removed). That means this
17:41:33 crash ran on the last successfully-compiled build from *before*
that session's edits — i.e. still carrying finding #10's guard
(`GetPuppetStateBlackboard()` check) but **not** the `GetAIComponent()`/
`GetVehicleComponent()` guards, and definitely not the fix below (which
didn't exist yet at the time this crash happened).

This means the crash's evidence says nothing about whether the

## New leading hypothesis: unscoped `ChangeHighLevelState`, not a missing null guard

Independently of REDscope's evidence, a re-read of `SpawnRequestFinished`'s
first loop turned up a **scope bug**, not another missing null check:

```
if !gotModTag && NPCManager.HasTag(candidatePuppet.GetRecordID(), n"GRModPuppet") {
    puppet = candidatePuppet;
    gotModTag = true;
    gangHandler = reinSystem.GetFactionHandler(puppet);
}
if IsDefined(candidatePuppet.GetPuppetStateBlackboard()) {
    NPCPuppet.ChangeHighLevelState(candidatePuppet, gamedataNPCHighLevelState.Combat);
}
```

The `gangHandler` assignment is correctly gated behind the `GRModPuppet`
tag — only this mod's own spawned puppets get touched. The
`ChangeHighLevelState` call sitting right after it has **no such gate**: it
ran on every puppet in `requestResult.spawnedObjects`, from *any* spawn
request. `DynamicSpawnSystem` is a shared vanilla system — every mod's and
every vanilla subsystem's spawn completions funnel through the same
`SpawnRequestFinished`, so this call was forcing arbitrary, unrelated NPCs
(other mods' puppets, vanilla quest/ambient/combat spawns) into `Combat`
high-level state, unconditionally.

Every fix applied to this function up to this point (finding #2, finding
#10, this session's component guards) narrowed the null-safety of that
same call site without ever questioning whether it should be running on
those NPCs at all. This crash's `combat: yes` live state fits well: a busy
fight pulls in many `DynamicSpawnSystem`-driven spawns from all directions,
maximizing exposure to this unscoped call.

**Fix applied**: removed the `ChangeHighLevelState` call from the unscoped
branch entirely (it was never needed there — the freshly-spawned puppet's
own combat AI already handles engaging, and this mod's own reinforcement
puppets get their combat behavior from being tagged/handled elsewhere).

## Status: CONFIRMED via reliable repro

The user found a reliable repro and ran it both ways on the clean
17:47:17+ build:

1. Enter combat at a location inaccessible by road — spawned reinforcements
   end up far away and/or out of line of sight, making it even more
   obviously wrong to force their combat state than in the general case.
2. The upstream/original `ReinforcementsSystem` mod (this mod's own
   ancestor — see project memory on the fork relationship) calls its own
   backup against the player — i.e. a spawn request **not** tagged
   `GRModPuppet`, since it's the other mod's own reinforcement call, not
   this one's.
3. Player defeats all local combatants; combat ends.
4. The original mod's spawn request completes and gets funneled through
   this mod's wrapped `SpawnRequestFinished` (shared vanilla method — every
   mod's and vanilla's own `DynamicSpawnSystem` completions pass through
   it). The unscoped `ChangeHighLevelState` call fires on those non-`GRModPuppet`
   NPCs.
5. Player re-enters combat (vanilla `DynamicSpawnSystem` behavior on new
   spawns) — **and the game crashed immediately at this exact point, every
   time, with the call present.**
6. With the call removed: identical sequence, no crash.

This nails down not just that the call was the fault site, but the
specific circumstance: it's the combat-end → new-spawn → combat-re-entry
transition where the vanilla high-level-state machinery is already doing
its own state changes for those NPCs, and this mod's parallel, unscoped
`ChangeHighLevelState` call was racing or conflicting with that — on NPCs
it was never supposed to be touching in the first place.

Superseded the "not yet proven" status from the initial write-up — this is
now a confirmed root cause, not a leading hypothesis.
