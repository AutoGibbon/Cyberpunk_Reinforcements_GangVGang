**Ran on a stale, pre-fix build.** A compile error (`UNRESOLVED_METHOD`,
`DynamicSpawnSystem.reds:97`, wrong type on the 17:08:24 session's own fix)
logged at 17:32:22 meant `final.redscripts.modded` never updated for this
launch — RED4ext silently ran the last successfully-compiled cache from
before that session's edits. New process note this produced:
[diagnosing-crashes.md](../../_shared/diagnosing-crashes.md)'s
"confirm the build actually compiled" check. This build still carried
finding #10's guard but not the 17:08:24 component guards.

**Real bug, found independently of the stale-build mixup**: a fresh read
of the first loop found a scope bug, not another missing null guard —
`NPCPuppet.ChangeHighLevelState(candidatePuppet, ...)` ran on **every**
puppet in `requestResult.spawnedObjects`, unlike the adjacent
`gangHandler` assignment right above it which is correctly gated behind
the `GRModPuppet` tag check. `DynamicSpawnSystem` is shared vanilla
infrastructure — this was forcing arbitrary unrelated NPCs (any mod's,
any vanilla spawn) into `Combat` state game-wide. See the "Beyond null
guards" note in
[diagnosing-crashes.md](../../_shared/diagnosing-crashes.md).

**Fix**: removed the `ChangeHighLevelState` call from the unscoped branch
entirely.

**Status: CONFIRMED via reliable repro**, run both ways on the clean
17:47:17+ build: enter combat somewhere reinforcements can't reach by
line of sight → the upstream `ReinforcementsSystem` mod (not this mod's
tagged spawns) calls its own backup → player wins → that spawn funnels
through this mod's `SpawnRequestFinished` → player re-enters combat as new
spawns arrive (vanilla behavior) → crash every time with the call present,
no crash with it removed. Resolved; a future recurrence on a build with
this fix is a new bug. Full batch context:
[crash-audit-2026-08-30.md](../crash-audit-2026-08-30.md).
